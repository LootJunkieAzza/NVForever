## 1. Rules for this queue (owner, 2026-10-20)

- **One item at a time.** Start an item only after the one before it has opened its PR. One
  item, one branch, one PR. Do not start follow-up sessions or fold two items together.
- **Never merge.** Open the PR and leave it; the owner's watcher merges.
- **Decide, don't ask.** Where the documentation or the original leaves a choice open, make it,
  tag it `[hypothesis]` and record it in the PR and the spec note.
- **CLAUDE.md applies in full**: clean room (no leaked source; nv-rs for format facts only,
  never its code; nif.xml as documentation only), every claim tagged `[documented]` (cite),
  `[observed]` or `[hypothesis]`, no game data committed, never write into the game folder.
- **Spec first.** Write the behaviour in plain language in `docs/spec-notes/` (or the named
  design note) before the code.
- **Checks**: the ones `python tools/smoke plan` lists, before every push. Add a `[[scenario]]`
  to `tools/smoke/scenarios.toml` when a log line can show the feature; after merging main
  into a branch run `python tools/smoke verify`.
- **Fetch origin/main first**, and again before committing: main moves many times a day.
- **Smoke**: worker sessions do not run the game. If this machine has the game and holds the
  game locks, it may run the new scenario itself and say so in the PR; otherwise the PR says
  the scenario has not been run.
- **Update** `docs/status.md` (the system's row), `docs/outstanding.md` (strike or reword the
  item) and the outcome table in §4 of this file with each PR.

Each item below is a brief: what to build, where to look, what "done" means beyond the rules
above.
