# Android performance controls and opt-in thermal adaptation

[design] The existing frozen performance packet is preserved. This increment ports its three aggregate presets and four world-resolution choices onto the current Android source. Battery selects the actual frame limiter at 30 FPS and existing FSR Performance (50% dimensions); Balanced 60 FPS and FSR Quality (67%); Quality 60 FPS and native rendering. Resolution choices use the actual existing FSR renderer and its capability checks, not a display-density or UI-size change. Unsupported FSR is explained and refused; stored requests survive with native fallback. A separate mobile FPS row offers 30 and 60 through the existing canonical frame-cap row. Individual canonical settings remain authoritative and persist in the existing INI. Other graphics settings stay unchanged.

[documented] Android PowerManager thermal-status listener/current status are API29; getThermalHeadroom is API30 and can return NaN when unsupported or queried too often. Some devices report NONE despite heating, so status is not a temperature or cooling guarantee. Sources: https://developer.android.com/reference/android/os/PowerManager and https://developer.android.com/games/optimize/adpf/thermal . Sampling headroom at most once every10seconds follows its documented rate bound; no ADPF performance hints or CPU governor changes are made.

[design] Automatic thermal adjustment is an explicit persisted OFF-by-default consent switch. It never rewrites Graphics, FramePace, preset names, custom settings or their INI values. The actual frame limiter reads a temporary effective cap; upscaler follow_request resolves a temporary FSR quality. Preset and manual edits take effect as the new baseline even while warm. Native or DLSS choices never automatically enable FSR. Existing FSR quality may become cheaper, never more expensive; unsupported FSR follows the normal renderer fallback.

[design] Warm means status MODERATE or headroom>=0.8, sustained5seconds; temporary cap45 and at most FSR Balanced. Hot means status SEVERE or above or headroom>=1.0; immediate cap30 and at most FSR Performance. Lower manual caps and cheaper manual FSR qualities remain lower. Recovery requires60continuous seconds at NONE/LIGHT with absent headroom or headroom<0.65, recovers one level at a time, and restarts the60second cool interval. Unknown readings clear the temporary budget; they are never interpreted as cool for hysteresis. No feedback or stale feedback (>25seconds), background and failed listener setup use manual settings and show unavailable/paused state. Thermal levels and history are session-only. Gaps greater than25seconds reset warming/cooling observation timers without treating the gap as sustained feedback.

[design] AndroidPerformance owns only PowerManager/listener and a Handler sample task. It starts after Activity resume, samples immediately, polls each10seconds, unregisters and invalidates generation before pause/destroy. Stale queued callbacks cannot update a later generation. snapshot is a bounded four-number string read through the existing JNI Activity string boundary; no identifiers, logs, paths or device telemetry. The controller-owned GameActivity receives a separate hook patch, with no window/insets/input changes.

[design] Validation includes actual Java host lifecycle/state tests, SDK35 compile of the adapter, pure Rust policy replay (threshold/hysteresis/unsupported/lifecycle/manualcaps), and authored combined App/settings tests confirming canonical values and persistence survive thermal changes and actual UpscalerStatus receives adjusted quality. Root admits the larger engine checks separately. No phone, GPU or runtime performance gain is claimed from source tests.
